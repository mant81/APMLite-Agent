# APMLite 개발 절차

## 기준선

주요 기능은 WAS 모니터링이다. 모든 기능·성능·대시보드 작업의 기본 벤치마크는 기준 APM 제품이며 제품명은 문서에 직접 기록하지 않는다. 각 변경은 다음 중 하나로 기록한다: `parity`(동등한 동작), `partial`(일부 대응), `gap`(미지원), `unknown`(측정 필요). 기준 제품의 내부 구현을 추측하지 말고 관찰 가능한 사용자 기능과 측정값만 비교한다.

우선 비교 항목은 접속자 수, TPS, 동시 접속자 수, 히트 수, JVM/GC 지표, WAS 트랜잭션·응답시간, JDBC SQL 실행 추적, 느린 쿼리·에러 집계, 스레드 상태, 서비스별 대시보드, 샘플링 주기·오버헤드, 히트 수 기반 경고 분석, 데이터 보존과 접근 제어다.

## 최상위 안전 전제

모니터링은 대상 서비스에 절대로 영향을 주면 안 된다. 계측 예외는 대상 요청으로 전파하지 않고, DB·네트워크·대시보드 장애는 관측 데이터 손실로 끝나야 한다. 서비스 안정성이 불확실하면 수집을 줄이거나 버린다.

1. `git status`, README, `pom.xml`, 소스와 기존 산출물을 확인한다.
2. 변경 목적을 구현·보안·호환성·성능 관점으로 나누고 완료 기준을 정한다.
3. 수정 전 재현 가능한 테스트 또는 smoke 절차를 작성한다.
4. 구현 후 Maven 빌드와 테스트를 실행한다.
5. 실제 JVM에 `-javaagent`를 연결하고 `/api/health`, `/api/overview`, `/api/timeline`, `/api/sql/top`, `/api/sql/slow`를 확인한다.
6. JDBC 관련 변경은 PreparedStatement 반환 타입, 예외 경로, 파라미터 비밀정보 노출을 별도로 검토한다.
7. 결과를 `docs/apmlite-development/`에 남기고, 미검증 항목은 명확히 표시한다.
8. 결과 보고에는 기준 APM 대비 상태(`parity`/`partial`/`gap`/`unknown`)와 측정 조건을 포함한다.
9. 접속자 수·TPS·동시 접속자 수·히트 수·히트 수 기반 경고 분석은 필수 WAS 기능으로 취급한다. 현재 구현에 없으면 `gap`으로 기록하고 수집 지점과 집계 주기를 먼저 설계한다.
10. SQL 모니터링은 시간 흐름 기반 잔디형 히트맵을 기본 화면으로 설계한다. 실행 시간, 실행 건수, 오류 상태를 점과 색상으로 표현하고 3초 미만은 초록색, 3초 이상 10초 미만은 노란색, 10초 이상은 붉은색으로 표시하되 SQL 파라미터와 비밀정보는 저장하지 않는다.

## 역할 분리

- implementation: 소스와 설정을 최소 범위로 수정한다.
- review: 실제 코드의 줄과 호출 경로를 근거로 결함을 분류한다.
- qa: 테스트 결과와 실행 로그로 동작을 검증한다.

## 금지 사항

- 비밀값을 파일·로그·메시지에 기록하지 않는다.
- 검증을 통과시키기 위해 TLS·서명·체크섬 검증을 끄지 않는다.
- 테스트가 없는 상태를 성공으로 보고하지 않는다.
